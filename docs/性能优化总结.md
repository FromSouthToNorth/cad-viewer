# DXF 大图纸加载与渲染性能优化总结

> 项目：realdwg-web（解析核心）+ cad-viewer（查看器）
> 目标图纸：`F:\gis\CAD\cad\data\JKYHMKA01A01yh3m.dxf`（95MB、AC1032、GBK/ANSI_936、389,328 个实体，mxdraw 生成的矿图）
> 文档日期：2026-08-18

---

## 1. 背景与问题

- 两个项目打开较大 DXF 图纸"巨卡"：加载过程长时间无响应、界面假死。
- 修复加载卡顿后，加载该矿图仍会在 16% 处永久卡死。
- 滚动/缩放时，已渲染的图层会丢失（详见第 6 节，坐标范围过大是直接原因）。

## 2. 根因分析（两层）

### 2.1 解析层（realdwg-web / @mlightcad/data-model）

- `AcDbNativeDxfConverter` 强制同步解析（`useWorker` 硬编码 false），95MB 文件在主线程上解析，长时间阻塞 UI。
- 解析器热路径（行读取、group code 解析、类型判断）存在大量小对象分配和字符串裁剪。
- 文件为 ANSI_936 (GBK) 编码，走 legacy-codepage 全量解码路径，95MB 文本全量解码后峰值堆内存约 1.6GB。

### 2.2 渲染层（cad-viewer / three-renderer）

- 默认非渐进式渲染：解析完一次性建 38 万实体的渲染对象，期间 rAF 被饿死（浏览器实测 12s+ 无帧）。
- 所有批次 `frustumCulled = false`，不做视锥剔除。
- `RTE_REBASE_THRESHOLD = 1e6` 的分批策略：超过阈值的实体走 unbatch 路径，此文件全部实体都超阈值（见第 6 节）。
- 大坐标（千万级）直接以 float32 传入 GPU，无全局原点平移，缩放时精度崩坏（第 6 节）。

### 16% 卡死专项修复（realdwg-web）

- **根因**：该文件 `$HANDSEED = FFFFF10000002B`，十进制超过 `Number.MAX_SAFE_INTEGER`（2^53-1）。
  `generateHandle()` 用浮点 `_maxHandle++`，超过安全整数后自增结果不变 → `generateUniqueHandle` 死循环。
- **修复**：`packages/data-model/src/database/AcDbDatabase.ts` 引入 `_maxHandleBig?: bigint`：
  - `generateHandle()` 在超过 `MAX_SAFE_INTEGER` 后切换到 BigInt 计数
  - `initializeHandleSeed()` / `updateMaxHandle()`（内部 `trackMaxHandle()`）BigInt 感知
  - 测试：`AcDbDatabase.spec.ts` 新增回归用例，8/8 通过；全套 821/821 通过
- **验证**：该文件解析 4.5s（3 次最优）、389,328 实体、峰值堆 1593.6MB；标准夹具无回退
  （lines-100000: 772ms、mixed-100000: 949ms、circles-50000: 411ms）。

### DXF 词法解析移入 Web Worker（realdwg-web）

- **切分点**：`AcDbDxfPairReader`（字节 → 类型化组码对）是唯一的 CPU 密集纯计算环节；
  其后的 `AcDbDxfDocumentReader` / 实体 `dxfIn` 直接写 `AcDbDatabase` 对象图，不可结构化克隆，留在主线程。
- **实现**：
  - `packages/data-model/src/base/AcDbDxfPairWire.ts`（新增）：pair 流的 SoA 线格式
    （`codes: Int32Array`、`types: Uint8Array`、`numbers: Float64Array`、去重字符串表、long 十进制字符串、binary 侧数组），
    `acdbDrainDxfPairs`（worker 内抽干）+ `acdbMakeDxfPairArrayReader`（主线程回放，实现同一 `AcDbDxfPairReader` 接口）。
  - `packages/data-model/src/dxf/AcDbDxfParserWorker.ts`（新增）+ `vite.config.worker.ts`：构建产物 `dist/dxf-parser-worker.js`。
  - `AcDbWorkerManager` / `AcDbBaseWorker` 扩展：`{id, type:'progress', progress}` 进度消息与成功响应的 transfer 列表（typed array 零拷贝回传）。
  - `AcDbNativeDxfConverter`：默认 `useWorker: true` + `/assets/dxf-parser-worker.js`；worker 不可用（Node、bundle 缺失、任务失败）自动回退主线程流式解析
    （发往 worker 前 `data.slice(0)` 复制，回退输入不受 transfer 影响）。进度映射：worker 词法解析 1–10%，主线程语义构建 10–18%，ENTITY 20–98% 不变。
- **行为不变**：主线程回放同一 pair 流进入同一 filer/document-reader 管线，表/实体/属性链接/ACDSDATA 等语义零改动；
  单测 `AcDbDxfPairWire.spec.ts` 做 pair 级无损回环断言（含 bigint long、310 binary、空流）。

## 6. 滚动缩放图层丢失诊断（坐标范围过大，已证实）

对目标文件实测坐标分布（`tools/bench/scan-coords.cjs`）：

| 区间 | ENTITIES | BLOCKS |
| --- | --- | --- |
| X | [-82,664.7, 39,652,926.8] | [-25.0, 17,247.0] |
| Y | [-82,664.7, 39,458,238.4] | [0, 8,658.8] |
| Z | [0, 19,730,366.2] | [0, 19,730,366.2] |
| 最大绝对值 | 3.965e7 | 1.973e7 |
| NaN 坐标 | 0 | 0 |

关键事实：

1. **全部 389,330 个实体都含 |坐标| ≥ 1e6**（无一例外），坐标是未归零的高斯投影值
   （八位数字）。注意：**实际运行走的是批处理路径**——`AcTrRenderContext` 默认策略是
   `alwaysBatchDrawPolicy`（`AcTrRenderContext.ts:41`），带 1e6 阈值的
   `defaultBatchDrawPolicy` 并未在生产路径启用（早期诊断"100% unbatch"结论有误，特此更正）。
   批容器本身已按批原点 rebase 顶点（写 float32 前先减原点，容器 `position` 为 JS double），
   因此普通线/圆弧/文字/点在大坐标下是精确的。
2. 75 个图层全部包含 ≥1e6 坐标；大图层（勘查线、采区边界等）的实体本身横跨 39.5M 范围。
3. 顶点以 float32 存 GPU：在 [33.5M, 67.1M) 量级 float32 的 ulp 为 4（单位）。**真正把
   千万级坐标"烧进" float32 的只有少数构建路径**（详见 6.5 节）：图案/实心填充与图像用
   `THREE.ShapeGeometry` 直接对 WCS 点三角化；上游 data-model 的 `AcDbFace`/`AcDbTable`/
   `AcDb3dSolid` 用 `new Float32Array(世界坐标)` 打包线段——这些量化发生在任何 rebase
   之前，无法事后恢复。短线段/填充边界被量化到 4 单位网格 → 放大到细节尺度时三角形退化、
   填充塌缩 → 图层"消失"。
4. 相机矩阵链在 JS 双精度中计算（相机与物体的千万级平移在相乘时相消，`modelViewMatrix`
   的值本身很小），**不需要场景级/相机级平移**。但相机 near/far 固定 0.1/1000、相机 z=500
   只覆盖约 1500 单位的世界 Z 带，本图 Z 高达 19.7M 的实体被裁剪永远不可见（与缩放无关的
   独立问题）。
5. 与视锥剔除无关：所有批次及 unbatched 克隆均 `frustumCulled = false`
   （`AcTrBatchedLine.ts:101`、`AcTrBatchedGroup.ts:2269` 等）。
6. 文件头 `$EXTMIN (-5512, -7953, -82665)` 与实际实体范围不符（只覆盖原点附近一角），
   依赖头部的取整/适配逻辑会得到错误范围。
7. 部分实体 Z 达 19.7M，深度缓冲在此量级同样失去分辨率，可能叠加闪烁。

**结论：图层在滚动缩放时丢失，正是坐标范围过大导致的**——根因是千万级世界坐标被少数
构建路径直接烧进 float32，加上固定近远裁剪面截断了高 Z 实体。修复采用**构建期原点平移**
（在进入 float32 之前归零 + 上游双精度传递 + 相机深度范围适配），已实施，见 6.5 节。

## 6.5 原点平移修复（已实施）

思路：不动场景图/相机（矩阵链在 JS 双精度下本就安全），把"归零"前移到**所有写入
float32 的点**上。
