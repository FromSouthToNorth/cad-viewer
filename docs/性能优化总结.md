# DXF 大图纸加载与渲染性能优化总结

> 项目：realdwg-web（解析核心）+ cad-viewer（查看器）
> 目标图纸：`F:\gis\CAD\cad\data\JKYHMKA01A01yh3m.dxf`（95MB、AC1032、GBK/ANSI_936、389,328 个实体，mxdraw 生成的矿图）
> 文档日期：2026-08-18

---

## 1. 背景与问题

- 两个项目打开较大 DXF 图纸"巨卡"：加载过程长时间无响应、界面假死。
- 修复加载卡顿后，加载该矿图仍会在 16% 处永久卡死。
- 滚动/缩放时，已渲染的图层会丢失（详见第 6 节，坐标范围过大是直接原因）。

## 2. 根因分析（两层）

### 2.1 解析层（realdwg-web / @mlightcad/data-model）

- `AcDbNativeDxfConverter` 强制同步解析（`useWorker` 硬编码 false），95MB 文件在主线程上解析，长时间阻塞 UI。
- 解析器热路径（行读取、group code 解析、类型判断）存在大量小对象分配和字符串裁剪。
- 文件为 ANSI_936 (GBK) 编码，走 legacy-codepage 全量解码路径，95MB 文本全量解码后峰值堆内存约 1.6GB。

### 2.2 渲染层（cad-viewer / three-renderer）

- 默认非渐进式渲染：解析完一次性建 38 万实体的渲染对象，期间 rAF 被饿死（浏览器实测 12s+ 无帧）。
- 所有批次 `frustumCulled = false`，不做视锥剔除。
- `RTE_REBASE_THRESHOLD = 1e6` 的分批策略：超过阈值的实体走 unbatch 路径，此文件全部实体都超阈值（见第 6 节）。
- 大坐标（千万级）直接以 float32 传入 GPU，无全局原点平移，缩放时精度崩坏（第 6 节）。

### 16% 卡死专项修复（realdwg-web）

- **根因**：该文件 `$HANDSEED = FFFFF10000002B`，十进制超过 `Number.MAX_SAFE_INTEGER`（2^53-1）。
  `generateHandle()` 用浮点 `_maxHandle++`，超过安全整数后自增结果不变 → `generateUniqueHandle` 死循环。
- **修复**：`packages/data-model/src/database/AcDbDatabase.ts` 引入 `_maxHandleBig?: bigint`：
  - `generateHandle()` 在超过 `MAX_SAFE_INTEGER` 后切换到 BigInt 计数
  - `initializeHandleSeed()` / `updateMaxHandle()`（内部 `trackMaxHandle()`）BigInt 感知
  - 测试：`AcDbDatabase.spec.ts` 新增回归用例，8/8 通过；全套 821/821 通过
- **验证**：该文件解析 4.5s（3 次最优）、389,328 实体、峰值堆 1593.6MB；标准夹具无回退
  （lines-100000: 772ms、mixed-100000: 949ms、circles-50000: 411ms）。

## 6. 滚动缩放图层丢失诊断（坐标范围过大，已证实）

对目标文件实测坐标分布（`tools/bench/scan-coords.cjs`）：

| 区间 | ENTITIES | BLOCKS |
| --- | --- | --- |
| X | [-82,664.7, 39,652,926.8] | [-25.0, 17,247.0] |
| Y | [-82,664.7, 39,458,238.4] | [0, 8,658.8] |
| Z | [0, 19,730,366.2] | [0, 19,730,366.2] |
| 最大绝对值 | 3.965e7 | 1.973e7 |
| NaN 坐标 | 0 | 0 |

关键事实：

1. **全部 389,330 个实体都含 |坐标| ≥ 1e6**（无一例外），坐标是未归零的高斯投影值
   （八位数字），全部超过 `RTE_REBASE_THRESHOLD = 1e6`（`AcTrBatchDrawPolicy.ts:15`），
   **100% 实体走 unbatch 路径** → 38 万个独立绘制对象，无合批收益。
2. 75 个图层全部包含 ≥1e6 坐标；大图层（勘查线、采区边界等）的实体本身横跨 39.5M 范围。
3. 顶点以 float32 存 GPU：在 [33.5M, 67.1M) 量级 float32 的 ulp 为 4（单位），
   短线段/注记的顶点被量化到 4 单位网格上。
4. 渲染器**没有全局原点平移**：正交相机直接在世界坐标中移动，modelView 矩阵以 float32
   上传 GPU。缩放时 view 平移量即相机坐标（千万级），每帧矩阵量化 → 放大到细节尺度时
   顶点塌缩、零长度线段被剔除 → 图层"消失"（注记/点/短线图层最先丢）。
5. 与视锥剔除无关：所有批次及 unbatched 克隆均 `frustumCulled = false`
   （`AcTrBatchedLine.ts:101`、`AcTrBatchedGroup.ts:2269` 等）。
6. 文件头 `$EXTMIN (-5512, -7953, -82665)` 与实际实体范围不符（只覆盖原点附近一角），
   依赖头部的取整/适配逻辑会得到错误范围。
7. 部分实体 Z 达 19.7M，深度缓冲在此量级同样失去分辨率，可能叠加闪烁。

**结论：图层在滚动缩放时丢失，正是坐标范围过大导致的**——根因是千万级世界坐标 +
float32 渲染管线缺少原点平移（origin shifting），叠加 1e6 阈值使全部实体退化为
unbatch。修复方向（属 M3+，尚未实施）：

- 渲染期原点平移：场景根节点按相机目标平移（或相机固定在原点、场景相对平移），
  使着色器内坐标始终在低量级；
- 转换期顶点整体归零：解析/建图阶段将全图顶点重定基到局部原点（分批已按批原点
  rebase，但批次容器矩阵仍带千万级平移，需一并处理）；
- 重新设计大坐标分批策略（当前 1e6 阈值对本文件无意义）。

## 7. 遗留工作（M3+，待真实 GPU 环境实施）

1. **大坐标原点平移（最高优先级，本次诊断新增依据）**：见第 6 节。
2. 分批槽级视锥剔除：恢复对 `frustumCulled=false` 批次的有效剔除。
3. 移除/上调 1e6 unbatch 阈值并配套精度策略。
4. 图纸空间视口候选剔除（paper-space viewport culling）。
5. 圆弧细分 LOD、样条拟合 Thomas 算法（O(n³)→O(n)）。
6. DXF 解析移入 Web Worker。
7. 解析器侧：AcCmObject set 快速路径、实体工厂默认几何消除。
8. GBK 窗口化解码（当前峰值堆 ~1.6GB）。
