## 2. M1 — 进度回退修复

### M1-1 drain 期间数字不再回退(主因)

- **文件**:`cad-viewer/packages/cad-simple-viewer/src/app/AcApOpenFileProgressController.ts:189-231`
- **方案**:`holdUntilSceneIdle` 轮询中删除 `setProgress(drain*100)`(`:213-223`),drain 期间保持 `setProgress(undefined)`(数字隐藏、spinner + "正在渲染"文案,即注释本意)。数字从 100% 消失后不再以低值重新出现。
- **验证**:控制器单测(fake progress + busyGate 恒真 → 断言 `setProgress` 不再被小值调用);手工:>10 万实体图纸 progressive 打开,观察 overlay。
- **风险**:极低;回滚即恢复旧行。
- **收益**:消除用户感知的"进度重来"假象(最高优先级体验问题)。

### M1-2 全局加权分段进度(去掉 FETCH_FILE→CONVERSION 峰值归零)

- **文件**:`AcApOpenFileProgressController.ts:127-137`(normalize)、`:182`(updateOverlay 取整);`cad-simple-viewer/src/app/openFileProgress.ts`(isOpenFileProgressComplete)
- **方案**:

  2. `isOpenFileProgressComplete` 改为只判终态(`subStageStatus === 'END' && (subStage === 'END' || stage === 'FETCH_FILE')`,或 ERROR),**不再依赖 percentage ≥ 100**——重映射后 CONVERSION 的尾部 FETCH_FILE END 事件(原 100 现为 10)无法靠数值判定。
  3. 状态栏 `MlProgress.vue` 与 overlay 共用归一化输出,阶段文案随 `subStage` 显示(下载中/解析中/渲染中)。
- **验证**:单测覆盖 normalize 跨阶段单调性;URL 打开场景手工验证(下载 100% 不再归零)。
- **风险**:中——终态判定逻辑是 overlay 隐藏的唯一起点,需全量回归 `isOpenFileProgressComplete` 的调用点(`AcApOpenFileProgressController.updateOverlay`、`MlProgress.vue:59`)。
- **收益**:URL 打开路径的第二次 100→0 消失;进度语义清晰。

## 3. M2 — UTF-8 解析热路径

### M2-1 值行 span 级数值扫描(最大收益项)

- **文件**:`realdwg-web/packages/data-model/src/base/AcDbDxfPairReader.ts`
  - 窗口化 reader `readRaw`(`:447-470`):值行由 `readLine()`(切片)改为 `readLineSpan()` 取 `(start, end)`,仅 string 类值保留切片。
  - 新增 `parseAsciiValueSpan(code, text, start, end)`(`:206-242` 的 span 版):
    - **double**:手写快速路径 `[+-]?digits[.digits][eE[+-]digits]`(覆盖真实 DXF 全部数值形态),失败回退 slice+Number;
    - **int**:span 内跳过空白与尾部垃圾(等价 parseInt 语义),零分配;
    - **long**:同 int + BigInt 罕见回退;
    - **bool/handle**:span 首尾空白检查,无空白则免 trim;
    - **string/binary**:必须保留时再 slice(`decodeHexBinary` 改造为 span 入参)。
  - 同步改造 `acdbMakeAsciiDxfPairReader`(非窗口化路径)保持一致。
- **验证**:
  - 差分测试:对 utf8-mixed-100000、gbk-lines-300000、ascii-lines-300000 三夹具,新旧实现逐 pair 断言值相等(数值严格 `===`);随机 double 模糊测试(1e5 样本含 `1e20/.5/-0/1./E+3` 等边界)。
  - 基准:`bench-parse.cjs` 前后对比 + `reader-mem-compare.cjs` 内存对比。
- **风险**:中——数值语义必须与 `Number()` 完全一致;差分测试是硬门槛。
- **收益**:消除约 70% 值行分配(数值行),预计解析提速 10-20%、峰值堆降 ~10%,GC 卡顿减少。

### M2-2 UTF-8 有效性嗅探兜底(修乱码)

- **文件**:`AcDbDxfPairReader.ts:747-756`(`acdbCreateDxfPairReader` 编码判定)
- **方案**:当判定出的编码非 UTF-8 时,对前 256KB 做**严格 UTF-8 字节序列校验**(零分配字节扫描):若整段合法且含 ≥1 个多字节序列 → 视为 UTF-8 覆盖声明。GBK 中文(尾字节 ≥0x40、常见 0x80-0xBF 续字节在 GBK 中非法)几乎必然校验失败,误判率极低。
- **验证**:新增小夹具(UTF-8 字节 + `$ACADVER AC1015` + `$DWGCODEPAGE ANSI_936`)解析后中文不乱码;gbk-lines-300000 仍按 GBK 解析(回归)。
- **风险**:低;开关可配(默认开)。
- **收益**:修复国内工具"UTF-8 字节 + 陈旧头"图纸的文字乱码。

### M2-3 pair 池化(实验项,若收益 <5% 放弃)

- **事实约束**:`AcDbDxfFiler.readItem` 直接返回 pair 对象(`AcDbDxfFiler.ts:310-321`),`pushBackItem` 依赖对象同一性检测——不能无脑复用对象。
- **方案**:池 + 代数标记——池对象带 `generation`,pushBack 检测改为比较 `(pair, generation)`;回收仅限"未被 pushBack 且消费方同步用完"的 pair(parse 单线程、消费同步是既有不变量)。放在特性开关后,先出原型测收益。
- **验证**:bench 对比 + 全量 DXF 测试套件回归。
- **风险**:中高——别名/生命周期 bug 隐蔽;故放在 M2-1 之后、按收益决定去留。

### M2-4 后台标签页让门优化(低优先级)

- **文件**:`realdwg-web/packages/common/src/AcCmYieldToUi.ts`
- **方案**:`document.hidden` 时用 `setTimeout(0)`/`scheduler.postTask` 替代 rAF(后台 rAF 被节流至 1fps);前台保持 rAF 保证一帧绘制。
- **验证**:后台标签页打开大图计时对比。
- **风险**:低;影响面是全局让门,需跑大图前台路径回归确认无感。

### M2 实施结果(2026-08-20)

**M2-1 值行 span 级数值扫描 ✅ 已落地**

- `AcDbDxfPairReader.ts`:窗口化 + 全文双 reader 值行改 `readLineSpan()`,数值行零切片,999 注释行零切片;`acdbParseDoubleSpan`/`acdbParseIntSpan`/`acdbParseLongSpan` 手写快速路径,double 快速路径在 ≤15 位有效数字且 |指数| ≤ 22 的域内可证明精确(整数 mantissa 精确入 double、10^k 精确可表示、乘除只舍入一次),越域回退 slice+Number;bool/handle/binary 改 span 版,含 `-0` 语义对齐(`parseInt('-')→+0`、`parseInt('-0')→-0`)。
- 验证:`AcDbDxfPairReaderSpan.spec.ts`(10 万随机 double 模糊 × 双 reader + 3 万 int + 3 万 long,严格 `===`);旧 bundle 快照 vs 新 bundle 三夹具逐 pair 差分 567 万 pairs 零差异(`tools/bench/diff-old-new-reader.cjs`);data-model 全量 112 套 853 测全过。
- 收益:reader 纯解析 148→114ms(utf8, **-23%**)、441.7→349.4ms(gbk, **-21%**)、341.4→261.1ms(ascii, **-23.5%**);端到端 best:utf8 731.9→664.0ms(-9.3%)、gbk 2428.0→2281.5ms(-6.0%)、ascii 2188.1→2092.1ms(-4.4%);utf8 峰值堆 245.4→236.0MB(转换管线对象占大头,稀释了 reader 层收益)。

**M2-2 UTF-8 有效性嗅探 ✅ 已落地**

- 新增 `acdbValidateUtf8Prefix(bytes, 256KB)` 严格 RFC 3629 校验(过短/代理区/超长/4 字节边界按规范拒绝,窗口边界允许跨窗完成尾序列);仅当自动探测到旧代码页 + 全前缀合法 + 含 ≥1 多字节序列时覆盖为 UTF-8;`sniffUtf8: false` 或显式 `options.encoding` 可关闭。
- 验证:`AcDbDxfUtf8Sniff.spec.ts` 15 测全过(AC1015+ANSI_936 陈旧头实为 UTF-8 → 中文正确解码;真实 GBK 夹具回归不受影响);三夹具旧新差分仍零差异;gbk 端到端复测 2313ms 无回归。
- 已知边界:若 GBK 字节流恰好在整段内构成合法 UTF-8 序列(如"中文" GBK 字节 D6D0 CEC4)会误判——真实 GBK 文件 256KB 前缀内出现 <0xC2 前导或 <0x80 尾字节的概率接近必然,风险可忽略。

**M2-3 pair 池化 ❌ 放弃(有数据)**

- `tools/bench/pool-ceiling.cjs` 原型:64 槽环形池"理想版"(忽略 filer pushBack/`_lastRead` 引用保留的真实风险)在 utf8 夹具反而慢 6.8%、gbk 慢 5.3%——V8 新生代 bump 分配极快,复用可变对象破坏对象形状与逃逸分析,上限为负。
- 结论:不再实现(免去 filer 同一性协议改造的中高风险);原型脚本保留作决策记录。

**M2-4 后台标签页让门 ✅ 已落地**

- `AcCmYieldToUi.ts`:`accmYieldToUi`/`accmYieldForPaint` 在 `document.hidden` 时改用 `setTimeout(0)`(后台 rAF 被节流至 ~1fps 会拖慢协作式解析),前台保持 rAF 保证每片后出帧。
- 验证:`AcCmYieldToUi.spec.ts` 7 测全过,common 全量 18 套 60 测全过;后台标签大图计时需浏览器环境,留待集成验证。

**M5-2 样条带状求解 ✅ 已落地**

**M5-3 大 INSERT/hatch/ACIS 分批化:评估后暂缓(记录)**

- 现状复核:`AcDbRenderingCache` 已具备模板压实与实例化(`compacted clones share geometry buffers`,README 与 `AcTrGroup.fastDeepClone` 支撑),重复 INSERT 已从 O(实体) 克隆降至 O(材质) 克隆;同步 draw 管线内的剩余长任务(未压缩块 fastDeepClone、hatch 三角化、ACIS 线框解码)要切片需把 `worldDraw/subWorldDraw` 全链路改为可恢复的异步迭代,属计划预估中的"后续评估"级改造。
- 决策依据:本机无 GPU 环境无法测量分批收益;既有渲染缓存已消解最高频的克隆成本;改造面跨 data-model/three-renderer 两包且触及块渲染正确性核心。按计划纪律(收益为负或风险过高按数据放弃)暂缓,待真实 GPU 环境 profile 数据后决定。未修改代码。

**M5-4 槽级视锥剔除:评估后暂缓(记录)**

- 现状复核:批级剔除(`AcTrBatchedMixin.syncFrustumBounds`)已落地;槽级剔除需要在一次 draw call 内跳过中间槽,three.js 常规 `WebGLRenderer` 对普通 `BufferGeometry` 无 multi-draw 支持,拆 drawRange 多段绘制则把单批次拆回多次 draw call,与批处理目标相悖。
