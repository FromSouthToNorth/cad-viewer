# 高性能 JavaScript/TypeScript 技术分析报告

> 分析对象:本工作区(`cad-viewer` + `realdwg-web` 联合开发仓库)
> 分析维度:WebAssembly 集成、SharedArrayBuffer、Web Worker 多线程计算、内存管理
> 日期:2026-08-19

本工作区是 `cad-viewer`(three.js 渲染/查看器)与 `realdwg-web`(DWG/DXF 解析核心)的联合开发仓库,目标是大图纸(38 万实体、95MB DXF 矿图)的加载与渲染性能。

---

## 1. WebAssembly 集成:唯一一条 WASM 线 —— LibreDWG 解析 DWG

整个工作区**只有一个 WASM 用途**:把 GPL 许可的 LibreDWG(C 库,Emscripten 编译为 `libredwg-web.wasm`,约 10MB)放在独立的 Web Worker 里解析 DWG 文件,同时实现 **GPL 许可隔离**(GPL 代码只在 worker 里,主包保持 MIT)。

### 加载链路(`realdwg-web/packages/libredwg-converter/`)

- wasm 由 npm 包 `@mlightcad/libredwg-web` 提供,通过 Emscripten 胶水以 `new URL('libredwg-web.wasm', import.meta.url)` 相对 worker 脚本定位,用 `fetch` + `WebAssembly.instantiateStreaming` 流式编译,失败时回退 ArrayBuffer 实例化(`src/AcDbLibreDwgConverterUtil.ts:1-7`)。
- 构建配置(`vite.config.worker.ts`)有几个针对大 wasm 的关键决策:
  - **故意不用 `build.lib` 模式**(库模式会无视 `assetsInlineLimit` 把 10MB wasm 内联成 data URI 导致 webpack 挂起,issue #494);
  - `assetsInlineLimit: 0` 强制 wasm 作为独立兄弟文件输出;
  - 固定文件名 `[name][extname]` 便于部署脚本查找;
  - `base: './'` 使 wasm 可部署在任意路径或 jsDelivr CDN。
- `verify-build.mjs` 构建后校验:wasm 文件必须存在且 >1MB、**禁止** worker 内出现 `data:application/wasm`、主 bundle 禁止含 `WebAssembly`/`HEAP8` 等痕迹(防止解析器被打进主包)。
- 部署靠 `vite-plugin-static-copy`(各示例应用)或 Node 拷贝脚本(CLI runner、copy-workers.mjs)把 worker + wasm 一起拷到 `assets/` 或 `workers/`;CLI headless 静态服务器显式返回 `Content-Type: application/wasm`(`cad-simple-viewer-cli/src/runHeadless.ts:255`),保证流式编译可用。

没有用 Rust/wasm-bindgen 系的 wasm,源码中也没有直接调用 `WebAssembly.*` API(只存在于 Emscripten 胶水内)。

## 2. SharedArrayBuffer:完全没有使用

全仓搜索 `SharedArrayBuffer`、`Atomics.`、`crossOriginIsolated`、COOP/COEP 响应头均为**零命中**。17 个 vite 配置和 CLI 静态服务器都没有设置 `Cross-Origin-Opener-Policy` / `Cross-Origin-Embedder-Policy`。

线程间数据传递用的是经典的 **`postMessage` + Transferable 所有权转移**,而非共享内存:DWG 文件字节以零拷贝方式 transfer 进 worker(`data-model/src/converter/worker/AcDbWorkerManager.ts:157-163`)。因此页面不要求 crossOriginIsolated 环境,部署简单。WASM 也是单线程运行(无 pthreads)。

若未来要引入 SAB(如 WASM pthreads 或多 worker 共享几何缓冲),需要同时补 dev server headers 和部署层 COOP/COEP。

## 3. Web Worker 多线程:3 个 worker + 通用 worker 池框架

**架构上只有三类 worker,都是预打包成独立 JS 文件、运行时以 URL + `{ type: 'module' }` 构造**(没有用 Vite `?worker`、comlink、SharedWorker 或内联 Blob worker):

| Worker | 来源 | 职责 |
|---|---|---|
| `libredwg-parser-worker.js` | 本仓库 libredwg-converter 构建 | 在 worker 内加载 LibreDWG wasm,把 DWG 字节解析成 `DwgDatabase` JSON |
| `dxf-parser-worker.js` | 本仓库 data-model 构建(`vite.config.worker.ts`) | DXF 词法解析:字节 → 类型化组码对(pair)流,SoA 线格式零拷贝回传 |
| `mtext-renderer-worker.js` | 外部包 `@mlightcad/mtext-renderer`(只拷贝产物) | MText 文字排版、shaping、字形网格生成 |

### 通用 worker 框架(`data-model/src/converter/worker/`)

- `AcDbWorkerManager.ts`:worker 池(默认上限 4 并发),任务 ID 关联(`task_${n}_${timestamp}`),超时按文件大小线性放大(30s + 1s/MiB,上限 120s)。**输入是 ArrayBuffer 时通过 transfer 列表零拷贝转移 DWG 文件字节**;回传结果走结构化克隆(worker 可通过 `getTransferables` 钩子对成功响应启用 transfer 零拷贝,DXF pair 流即如此)。任务期间支持 `{ id, type: 'progress', progress }` 中间进度消息。
- `AcDbBaseWorker.ts`:worker 侧基类,统一 `{ id, input } → { id, success, data, error, errorCode }` 协议,`executeTask` 收到可上报进度的 task context,postMessage 失败时专门归类 `worker_oom` / `worker_timeout` 错误码。

### 设计取舍

放 worker 的都是**自包含、产出可传输数据**的重计算:DWG 整体解析、DXF 词法解析、文字排版。**实体转换(`processEntities`)与 DXF 语义构建(符号表/实体 `dxfIn`/属性链接)留在主线程**——它们直接写 `AcDbDatabase` 对象图,跨线程传输海量实体对象的序列化成本不划算。DXF 因此采用折中:worker 只把字节流词法解析成 pair 流(SoA typed arrays + 去重字符串表,transfer 零拷贝),主线程用数组支撑的 `AcDbDxfPairReader` 把 pair 流回放进与原先完全相同的 filer/document-reader 管线;Worker 不可用时回退主线程流式解析。主线程侧的长任务仍用 `AcDbBatchProcessing` 分块 + `accmYieldToUi` 时间预算让门(scheduler.postTask 优先、setTimeout(0) 兜底)做协作式多任务。无头 CLI runner 甚至用 `useMainThreadDraw: true` 强制 mtext 走主线程。

## 4. 内存管理:优化最密集的部分

### (a) 打包 TypedArray 批缓冲 + 槽位 free-list(渲染端核心模式,`three-renderer/src/batch/`)

- `AcTrBatchedMixin.ts:116-160` 按 `maxVertexCount` 预分配 Float32Array/Uint32Array(按顶点数选 Uint16/Uint32 索引);`reserveGeometryId` 把删除实体的槽位入池复用;扩容按 1.25 倍摊销;删除只置标志位,由 `optimize()` / `compactIndexedSlice` 压缩死数据。大量实体打包进单个 BufferGeometry 以减少 draw call。

### (b) 大坐标精度:RTE(相对原点渲染)

- 数据模型全程 `Float64Array` 保 WCS 双精度(`AcDb3dSolid.ts:376` 注释:"Float64Array keeps WCS double precision until the renderer rebases");
- 渲染端每个批次以几何包围盒中心建立世界原点,顶点就地改写为 Float32 局部坐标(`rebaseGeometryInPlace`),远距离几何按原点再分裂批次(`AcTrBatchDrawPolicy` 的 `RTE_REBASE_THRESHOLD`)。这正是仓库提交历史里"大坐标图层丢失修复"的机制。HTML 导出端同样做 centroid rebase + double 偏移。

### (c) CPU 侧内存主动释放(针对大图纸的特色做法,`cad-html-plugin/src/AcExViewerMemory.ts`)

- GPU 上传后把 `BufferAttribute.array` 替换为空 `Float32Array(0)` 并清 update ranges(交织缓冲用 Set 去重防重复释放);快照 DOM 中最大的 base64 字符串也显式移除。
- three.js 资源 99+ 处显式 `dispose()`,且对共享材质/缓存模板几何有意识跳过;高亮材质用 WeakMap 缓存、随源材质 dispose 自动驱逐。

### (d) 块参照实例化缓存而非 InstancedMesh

- 全仓**没有用 `THREE.InstancedMesh`**。块(INSERT)实例化靠 `AcDbRenderingCache` 单例 Map 模板缓存 + `compactForInstancing()` 同材质叶合并 + `fastDeepClone` 共享几何缓冲,使每次插入克隆成本是 O(材质数) 而非 O(实体数);缓存内还有 ByBlock 颜色 scratch 对象池、scratch 矩阵复用、自适应压缩阈值。只有宽线 Line2 用 `InstancedBufferGeometry` 实例属性。

### (e) 大 DXF 流式解析(`AcDbDxfPairReader.ts`)

- reader 契约明确**禁止把整个文件物化为 string[]**;64KiB 分块 `TextDecoder` 流式解码(`{stream:true}`);二进制数据以 `Uint8Array[]` 分块累积最后一次性拼接;解析期 `beginEventBatch()` 抑制 worldDraw,再 `endEventBatchChunked` 分块刷进度——配合 UI 让门,保证 95MB 文件打开时页面可响应。

### (f) 内存估算工具

`data-model/src/misc/AcDbMemoryEstimator.ts` 内置堆快照估算(注释说明 GPU buffer 与 converter worker/WASM 内存不在估算内),配合渲染缓存里的 profiling 计数器,说明团队对内存有持续观测手段。

## 总体评价

该项目的高性能策略是**务实组合**而非技术堆叠:

- **WASM** 仅用于 DWG 解析且工程化做得很细(防内联、构建校验、CDN 可部署);
- **多线程**只用两个 worker + transfer 零拷贝,刻意回避 SharedArrayBuffer 以免引入 COOP/COEP 部署要求;
- 真正的大头优化在**内存侧**——打包批缓冲、RTE 大坐标处理、GPU 上传后释放 CPU 数组、块模板缓存、流式 DXF 解析,这些都是针对"38 万实体矿图"这一具体场景的定向优化。

**遗留的潜在方向**:worker 回传的解析结果仍走结构化克隆(大图纸下有序列化开销);缓存均无 LRU 自动驱逐,长会话下依赖显式清理。
