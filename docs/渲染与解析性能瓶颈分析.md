# cad-viewer 渲染 + data-model 解析性能瓶颈分析(UTF-8 DXF 焦点)

> 分析对象:`F:\gis\bw-cad-view`(cad-viewer monorepo + realdwg-web)
> 目标场景:UTF-8 编码 DXF(AC1021+/`$DWGCODEPAGE: UTF-8`,text-heavy 中文图纸);基准夹具 100,000 实体
> 日期:2026-08-20(第二次更新;第一版为 GBK 焦点,本版以 UTF-8 为主并新增打开进度回退根因)

## 结论先行

1. **进度条"第一次到 100% 但没加载完、又回到 0% 重来"是三个机制叠加的结果,主因是两个进度域共用同一个数字**:CONVERSION(解析+实体 flush)到 100% 时,场景转换 drain(progressive batchConvert + 字形任务)才刚开始,`holdUntilSceneIdle` 的 50ms 轮询把 drain 的 0-1 比例重新画回同一数字进度条,表现为从 ~0% 重新爬升。另有 URL 打开时 FETCH_FILE→CONVERSION 的峰值归零、打开失败后 `regen()` 重开两个次要机制。
2. **UTF-8 解码已窗口化,解析内存大头已解决**:64KB 行对齐窗口化 reader 已泛化到所有"行安全"编码(UTF-8/GBK/Big5/Shift-JIS/EUC-KR/单字节页);第一版文档的"GBK 全量解码 1.6GB 峰值堆"条目已过时。仅 UTF-16 家族与未知编码标签仍走全量解码。
3. **解析剩余瓶颈**:值行逐行 `text.slice` + `Number()`(~80 万次/10 万实体)、pair 无池化、实体 dxfIn 临时对象、UTF-8 特有的编码判定风险(UTF-8 字节 + 陈旧头被按 GBK 解码)。
4. **渲染侧:批级视锥剔除已实现(第一版第 1 项已落地)**,仍存在的项:可见性切换整缓冲重传、MTEXT 逐实体 worker 往返、高亮掩码全量重建、optimize 尾部裸 `needsUpdate` 等。

## 〇、打开进度 100% → 0% 重来的根因(本次重点)

### 机制 1(主因):场景转换 drain 用同一数字从 ~0% 重新爬,progressive 大图必现

代码链:

1. DXF 转换器进度本身单调:`AcDbNativeDxfConverter.ts:22-25` 定义 PARSE=1~18、ENTITY=20~98,`emit(100,'END','END')`(`:133`)收尾。**这个 100% 的语义是"解析 + 实体 flush 完成",不是"场景就绪"。**
2. 此时 progressive 渲染的 `batchConvert` drain 才刚开始:`entityAppended` → `_convertQueue.push` → `void this.drainConvertQueue()`(`AcTrView2d.ts:1812-1813`)是异步逐批转换,大图时队列里仍有大量实体;`isProcessingEntities = _numOfEntitiesToProcess > 0 || _pendingGeometryJobs > 0`(`:663`)恒真。
3. `AcApOpenFileProgressController.updateOverlay`(`AcApOpenFileProgressController.ts:155-162`)发现 `isOpenFileProgressComplete` 为真后,检查 `isOpenFileWorkPending`(= `isProcessingEntities || progressiveFit.isActive`,门由 `AcApDocManager.ts:518-520` 注入)仍为真 → 进入 `holdUntilSceneIdle()`。
4. `holdUntilSceneIdle`(`:189-231`)先 `setProgress(undefined)` 把数字藏起来(`:204`),**但紧接的 50ms 轮询又把 drain 比例重新画回同一数字**:`setProgress(drain * 100)`(`:213-223`),而 `entityProcessingProgress = 1 - remaining/total`(`AcTrView2d.ts:685-697`)此时可能只有 2%~5%。用户看到:100% → 短暂空白 → 从 0% 附近重新爬升。**这不是重开文件,是同一个打开的第二个进度域。**

### 机制 2(次因):URL 打开时 FETCH_FILE → CONVERSION 强制峰值归零,多一次 100→0

`normalize()`(`AcApOpenFileProgressController.ts:127-137`)在阶段从 FETCH_FILE 切到 CONVERSION 时把 `_peak` 归零。`AcDbDatabase.openUri`(`AcDbDatabase.ts:2251-2348`)先发 FETCH_FILE 0→100(下载进度),再发 CONVERSION 0→100(解析),所以走 HTTP 加载的文件会看到两次回退:下载 100% → 0% 解析 → 100% → 0% drain。状态栏 `MlProgress.vue:58-59` 直接显示 `data.percentage`,不做任何阶段区分,故每次回退都可见。

### 机制 3(边缘):打开失败后 `regen()` 重开一轮进度

`onAfterOpenDocument` 失败分支调用 `this.regen()`(`AcApDocManager.ts:1761-1764`),而 `AcDbDatabase.regen()`(`AcDbDatabase.ts:2400-2410`)复用 `createConversionProgressHandler` 再发一轮 CONVERSION 0→100。解析在接近完成时抛错(如 flush 尾部),用户会看到进度到高位后归零重来。

### 为什么"第一次 100% 却没加载完"

CONVERSION END=100 只代表"解析+实体提交完成";`isOpenFileWorkPending` 仍为真代表"场景转换/字形/相机适配未完成"。文字多的中文图纸里 `_pendingGeometryJobs > 0`(字形与字体任务)会继续拖住该门,overlay 迟迟不消失,与机制 1 叠加放大"卡在 100% 后又重来"的观感。

### 修复方向(按收益排序)

1. `holdUntilSceneIdle` 轮询中**不要再 `setProgress` 一个低于已显示值的数字**:drain 期间保持数字隐藏、只转 spinner(代码注释本意即此,`:202-205`,轮询却把数字画回去了);或把 drain 映射到 99→100 区间;或与已显示值取 max。
2. 进度改为全局权重分段(fetch 0-10 / parse 10-30 / flush 30-60 / drain 60-100),去掉 FETCH_FILE→CONVERSION 的 `_peak` 归零(`:130-132`)。
3. 状态栏 `MlProgress` 与 overlay 统一使用同一归一化输出,阶段文案随 `stage/subStage` 显示,让用户知道"100% 是解析完成,渲染仍在继续"。

## 一、解析侧瓶颈(UTF-8 DXF,data-model)

### 1.1 已优化 / 与第一版的差异

- **窗口化解码已泛化**:`acdbCreateDxfPairReader`(`AcDbDxfPairReader.ts:712-770`)对 `acdbSupportsWindowedDecode` 通过的所有编码(UTF-8、GBK、Big5、Shift-JIS、EUC-KR、单字节页)走 64KB 行对齐窗口化 reader;仅 UTF-16 家族与 `TextDecoder` 不认识的标签走全量解码(`:768-770`)。多字节序列内不可能出现 0x0A/0x0D(UTF-8 续字节 ≥0x80,GBK 尾字节 ≥0x40),窗口行对齐安全。**第一版"GBK 全量解码 → 1.6GB 峰值堆"已解决。**
- BOM 跳过(`:387-396`)、group code 零分配扫描(`acdbReadDxfCodeFromChars`)、`$ACADVER`/`$DWGCODEPAGE` 头部探测只扫前几 KB(`acdbPeekDxfHeaderInfo`,`:59-102`)。

### 1.2 基准数据

UTF-8 夹具(新生成,见文末复现材料):AC1021 + `$DWGCODEPAGE: UTF-8` 无 BOM,100,000 实体(60% LINE / 20% LWPOLYLINE×4 顶点 / 10% CIRCLE / 10% 中文 TEXT),8.5MB:

| 夹具 | 实体 | 耗时 | 峰值堆 | 每实体 |
|---|---|---|---|---|
| utf8-mixed-100000(2026-08-20 实测) | 100,000 | **843ms**(best) | **237MB** | 8.4µs |
| mixed-100000(baseline,ASCII) | 100,000 | 998ms | 124MB | — |
| lines-100000(baseline,ASCII) | 100,000 | 761ms | 125MB | — |

中文 TEXT 实体使峰值堆约为纯线条图的 2 倍(字符串常驻 + 实体对象),但 843ms 的绝对耗时说明 UTF-8 解码本身已不是瓶颈;对比第一版的 389k 实体 GBK 矿图(4.5s / 1.6GB 峰值堆),窗口化后内存路径已完全不同。

### 1.3 剩余热点

1. **值行仍逐行 `text.slice` + `Number`/`parseInt`(CPU/GC 头号残余)**:窗口化 reader 的 `readRaw` 每个值行调 `readLine()`(`AcDbDxfPairReader.ts:447-460`)产生一次字符串切片,数值再走 `parseAsciiValue` 的 `Number/parseInt`(`:206-242`)。10 万实体 ≈ 80 万次分配,389k 实体矿图 ≈ 230 万次。修法现成:仿照已零分配的 code 扫描做 `(text, start, end)` 级数值扫描,仅 string 值保留切片(中文文本内容必须切片,数值行不必)。
2. **pair 对象无池化**:每个 pair 一个新对象,lookahead 仅一格、生命周期短、parse 单线程,可安全复用。
3. **实体 dxfIn 临时对象 + commit 开销**(与编码无关但占大头,延续自第一版):`AcDbLine` 每条 5-6 个临时向量/点对象;`commitEntity` 每实体 `ownerId` set + `parseInt(handle,16)`。
4. **让门仍是 `requestAnimationFrame`**(`AcCmYieldToUi.ts`):后台标签页 rAF 被节流至 1fps,后台打开大图显著变慢。转换路径已改用 `setTimeout(0)` 的先例值得推广到解析路径。

### 1.4 UTF-8 特有的编码判定风险

`acdbCreateDxfPairReader`(`:747-756`)对旧版本号(`supportsUtf8CodePage = false`)的图纸无条件信任 `$DWGCODEPAGE`。国内工具导出的 DXF 常见"UTF-8 字节 + 陈旧头 AC1015/ANSI_936",会被按 GBK 解码成乱码。建议增加合法 UTF-8 字节序列嗅探作为兜底(与窗口化机制天然兼容:多字节序列无换行字节),命中即改走 UTF-8。

## 二、渲染侧瓶颈(three-renderer,状态更新)

### 2.1 已解决(第一版第 1 项)

**批级视锥剔除已实现**:`AcTrBatchedMixin.ts:715-970` 在 `onBeforeRender` 做脏同步——几何变更后首帧计算聚合包围球(`computeBoundingSphere`,`:601-616`)再打开 `frustumCulled`,带全局开关 `_batchFrustumCullingEnabled`(默认 true),新增测试 `AcTrFrustumCulling.spec.ts`。构造函数仍初始 `frustumCulled = false`(`AcTrBatchedLine.ts:101` 等),脏期间保守全画,属正确语义。

### 2.2 仍存在的项(本次逐条复核)

1. **可见性切换整缓冲重传**:`AcTrIndexedBatchDrawVisibilityStrategy.ts:25-52` 隐藏槽时复制整段索引快照 + 裸 `needsUpdate`(无 `addUpdateRange`),切大图层时 MB 级上传。
2. **optimize 压实部分未限范围**:搬移段已加 `addUpdateRange`(`AcTrBatchedLine.ts:516-545`),尾部清零段(`:564`)仍裸 `needsUpdate`;flush 后每批一次 `optimize()`(`AcTrBatchedGroup.ts:1323`)不变。
3. **MTEXT 逐实体 worker 往返、无内容级字形缓存**:`AcTrMTextRenderer.ts:148-156` 每实体一次 `asyncRenderMText`,仅字体级缓存。UTF-8 中文图纸文字标签多 → 数千次往返;且 `_pendingGeometryJobs` 未清零期间 `isOpenFileWorkPending` 恒真,与进度问题机制 1 直接叠加。
4. **高亮掩码整张重建**:`AcTrBatchHighlightState.ts:194-230` 每 dirty 批次重建整张 `Uint8Array(w*h*4)` DataTexture。
5. **free-list 每次 reserve `sort + shift`**(`AcTrBatchedMixin.ts:223-243`):大删后连续新增可退化 O(n²),改单调栈/计数即可。
6. **转换期 shell dispose 误伤共享材质**:`AcTrEntity.disposeObject`(`AcTrEntity.ts:247-295`)仅 `sharesTemplateGeometry` 一个保护条件,批量路径共享的样式材质在 shell 被 dispose 时连坐 → program 重建。
7. **虚线高亮 lineDistance 无条件计算**(`AcTrBatchedLine.ts:310,453-454`):占顶点内存 ~25%,属必要成本但可考虑按需启用。
8. **缓存无 LRU**:`AcDbRenderingCache._blocks`(`realdwg-web/packages/data-model/src/misc/AcDbRenderingCache.ts:134`)与 `AcTrMaterialManager` 仅随文档关闭显式 clear。
9. **批级剔除的残余**:`computeBoundingSphere` 每次脏同步遍历全部槽;大坐标下批次按 `RTE_REBASE_THRESHOLD = 1e6` 分裂,散布全图的线/面仍产生大量批次容器(槽级剔除未做)。

### 2.3 已确认无问题(不重复优化)

交互缩放/平移不触发批次重建(RTE rebase 仅在入批时一次);框选命中(RBush 层次索引 + 每槽 drawRange 射线)与批量删除(单遍写指针压缩 + microtask 合并 optimize)为线性复杂度。

## 三、实体转换管线(延续自第一版,本轮未深挖)

- `worldDraw` 每实体固定开销:`isLayerDrawable` + `resolvedColor` + `lineStyle`(**每次调用分配新对象**,`AcDbEntity.ts:772-778,901-915`)+ 材质键模板串拼接,389k 实体 ≈ 1-3s drain 基座。
- 单实体长任务不可抢占:大 INSERT 同步重挂接、未压缩块 `fastDeepClone`、ACIS 线框解码、hatch 三角化;让门只在实体间检查。
- 样条拟合稠密高斯消元 O(n³)(`geometry-engine/src/util/AcGeNurbsUtil.ts`),解析阶段触发、单条不可打断;文档 M3#5 的 Thomas 算法仍未做。

## 四、建议优先级清单

| 优先级 | 项目 | 预期收益 |
|---|---|---|
| 1 | 修 `holdUntilSceneIdle` 数字回退(drain 期间数字保持隐藏或单调不减) | 消除"100%→0% 重来"假象 |
| 2 | 进度全局权重分段 + 去掉 FETCH_FILE→CONVERSION 峰值归零 | URL 打开不再双重回退 |
| 3 | 值行 char 级数值扫描(去 ~230 万次 slice/Number) | 解析再降 0.5-1s,GC 压力大减 |
| 4 | 编码判定加 UTF-8 有效性嗅探 | 修 UTF-8 字节 + 陈旧头图纸乱码 |
| 5 | MTEXT 内容级字形缓存 + 往返合并 | 多文字图纸打开提速、overlay 提前结束 |
| 6 | 可见性切换 / optimize 尾部 `addUpdateRange` | 图层开关、批量删除不再整缓冲重传 |
| 7 | pair 池化、lineStyle 缓存引用、free-list 去排序 | 解析与 drain 常数开销 |
| 8 | 高亮掩码局部更新、让门换 postTask/setTimeout、样条 Thomas O(n) | 交互与后台/特殊实体场景 |
